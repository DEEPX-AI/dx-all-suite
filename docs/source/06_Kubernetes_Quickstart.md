# Kubernetes Quickstart

> New to Kubernetes? Start with the [Kubernetes Beginner Guide](07_Kubernetes_Beginner_Guide.md), which explains each piece with a classroom analogy and hands-on examples.

Run DEEPX DX-M1 NPUs as native Kubernetes resources: request `deepx.ai/dx-m1: 1`
in a Pod spec and the scheduler places the Pod on an NPU node, with the device
node and runtime libraries injected automatically.

## Architecture

```
host (per NPU node)          k3s cluster
─────────────────────        ─────────────────────────────────────────
dx-runtime/install.sh   ──►  driver (dxrt-driver-dkms) + firmware + dxrtd
containerd CDI enabled       (enable_cdi=true, cdi_spec_dirs incl /etc/cdi)

Helm: dx-npu ──► NodeFeatureRule (PCI 1ff4 → deepx.ai/dx-m1.present)
              └► device-plugin DaemonSet → advertises deepx.ai/dx-m1
                   ├─ writes /etc/cdi/deepx.json  (device node + libs + dxcli)
                   ├─ writes NFD feature file → fw/driver version node labels
                   └─ serves deepx_npu_* Prometheus metrics on :9400
Pod requests deepx.ai/dx-m1: 1 → containerd injects /dev/dxrtN + runtime libs
```

Components (mirroring the proven NVIDIA stack layout):

| Component | Role |
|---|---|
| [dx-k8s-device-plugin](https://github.com/DEEPX-AI/dx-k8s-device-plugin) | Advertises `deepx.ai/dx-m1`, health checks, Pod allocation |
| CDI spec (generated by the plugin) | Injects `/dev/dxrtN`, runtime libs, and `dxcli` into containers |
| NFD integration | Node labels: presence, count, product, firmware/driver versions |
| `dx-npu` Helm chart | One-command install/upgrade of all of the above |

## Prerequisites

0. **Cluster tools.** Skip this step if you already have a Kubernetes cluster
   plus `kubectl` and `helm`.

    ```bash
    # k3s — a single-binary Kubernetes; installs kubectl too
    curl -sfL https://get.k3s.io | sh -

    # use kubectl without sudo
    mkdir -p ~/.kube
    sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
    sudo chown "$USER" ~/.kube/config

    # helm
    curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

    # jq — only used by the check commands in these docs
    sudo apt-get install -y jq

    kubectl get nodes      # STATUS Ready
    helm version
    ```

    On vanilla Kubernetes, install kubectl from the
    [official guide](https://kubernetes.io/docs/tasks/tools/) and helm from
    [helm.sh](https://helm.sh/docs/intro/install/).

1. **Each NPU node** — host driver, firmware, and runtime:

    ```bash
    cd dx-runtime && ./install.sh --runtime-only
    dxcli -s   # must list the NPU(s)
    ```

2. **containerd CDI enabled.** containerd 2.x turns CDI on by default (`enable_cdi =
   true`, spec dirs `/etc/cdi` and `/var/run/cdi`), so there is nothing to do. Check the
   version:

    ```bash
    sudo k3s ctr version | grep -m1 Version    # v2.x → done
    ```

    Only containerd 1.7 needs CDI switched on. On k3s, **do not** create
    `config.toml.tmpl` with just the CDI lines — k3s uses the template *instead of*
    its generated config, so the rest of the containerd settings would disappear.
    Start from the generated file and append:

    ```bash
    cd /var/lib/rancher/k3s/agent/etc/containerd
    sudo cp config.toml config.toml.tmpl
    sudo tee -a config.toml.tmpl <<'EOF'

    [plugins."io.containerd.grpc.v1.cri".cdi]
      enable_cdi = true
      cdi_spec_dirs = ["/etc/cdi", "/var/run/cdi"]
    EOF
    sudo systemctl restart k3s
    ```

    Either way, the smoke test below proves it: if `/dev/dxrt0` shows up inside the pod,
    CDI works.

## Install

```bash
helm install dx-npu oci://ghcr.io/deepx-ai/charts/dx-npu \
  -n dx-system --create-namespace --set nfd.enabled=true
```

Leave `nfd.enabled=false` (default) if the cluster already runs
node-feature-discovery.

Verify the NPU is schedulable and labeled:

```bash
kubectl get node -o json | jq '.items[].status.allocatable' | grep deepx.ai/dx-m1
kubectl get node --show-labels | grep -o 'deepx.ai[^,]*'
# deepx.ai/dx-m1.present=true, .count, .product, .fw-version, .driver-version
```

## Run a workload

Smoke test (thin image — everything arrives via CDI):

```bash
kubectl apply -f deploy/k8s/samples/test-pod.yaml
kubectl logs -f dx-m1-test
# shows /dev/dxrt0 and full `dxcli -s` device status from inside the Pod
```

Real inference with the suite runtime image. An init container fetches one
model into an emptyDir, then `dxrun` reports NPU time, latency, and FPS:

```bash
kubectl apply -f deploy/k8s/samples/inference-pod.yaml
kubectl wait --for=jsonpath='{.status.phase}'=Succeeded pod/dx-m1-inference --timeout=300s
kubectl logs dx-m1-inference -c inference
```

Any Pod becomes an NPU Pod with just a resource request:

```yaml
resources:
  limits:
    deepx.ai/dx-m1: 1
```

## Metrics

The device plugin serves Prometheus metrics on `:9400` (headless Service
`dx-npu-metrics`): `deepx_npu_up`, `deepx_npu_device_healthy`, and per-core
`deepx_npu_core_{temperature_celsius,voltage_millivolts,clock_mhz}`. Set
`metrics.serviceMonitor.enabled=true` when prometheus-operator is present.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `deepx.ai/dx-m1` missing from allocatable | Device plugin Pod not running — check `kubectl get pods -n dx-system` and that the node carries `deepx.ai/dx-m1.present=true` |
| No `deepx.ai/*` node labels | NFD not installed — set `nfd.enabled=true` or install NFD; without NFD, label manually: `kubectl label node <n> deepx.ai/dx-m1.present=true` |
| Pod scheduled but `/dev/dxrt*` missing | containerd CDI not enabled — apply the config.toml.tmpl change and restart k3s |
| `dxcli` reports no devices on host | Driver/firmware not installed — rerun `dx-runtime/install.sh`, then cold-boot if device init fails |
| Device reported unhealthy | Card present in sysfs but absent from `dxcli -s` — usually needs a host power cycle |
| `GLIBC_2.xx not found` running `dxcli` in a pod | The image's glibc is older than the host runtime's. DXRT v3.4.2 needs GLIBC_2.38 — use `ubuntu:24.04` or newer as the base |

Full chart values and details: `deploy/k8s/README.md`.
